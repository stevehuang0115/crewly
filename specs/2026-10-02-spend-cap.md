# Token usage: stats, daily caps (agent / team / total) and temporary boosts

Status: implemented (OSS `feat/token-usage-stats-caps`; supersedes the USD spend cap of #853 / PR #936)
Date: 2026-10-02

## Why

The orchestrator once used up the owner's whole DeepSeek balance in a week, and nothing stopped an
agent that was already spending. #853 added a per-agent daily cap in USD. The owner then set the
direction (2026-10-02):

- **count tokens, not dollars;**
- **do not tell subscription and API billing apart** (a Claude subscription has no bill per token,
  so a dollar figure was only ever "API-equivalent" and confusing);
- give per-team caps and a one-tap "boost for today".

Other limits, for contrast: `TeamBudgetGateService` refuses new work at claim time per team; the
runtime fallback reacts to a **provider's** usage limit by switching runtimes. A token cap is the
owner's own limit, per local day, and it **stops the agent**.

## 1. Token unit

One formula, `eventTokens(event)` in `services/monitoring/token-usage.service.ts`:

```
total tokens = input tokens (fresh + cached) + output tokens
```

- Cached input **counts in full**. It is reported beside the total (`cachedInput`), never left out.
- Every cap, boost, autopilot budget and stat uses this one function (directly, or through
  `TokenUsageService.getSessionUsageSince(...).totalTokens`).
- The ledger holds two event shapes; `eventTokens` normalises them:

| Source | `runtime` | `input` | `cachedInput` |
|---|---|---|---|
| In-process Crewly Agent runs (DeepSeek, …), `model = provider/model` | `crewly-agent` (inferred) | prompt tokens, cache hits **included** | the cache-hit part of `input` |
| Claude Code turns (`ClaudeTranscriptSync`) | `claude-code` (inferred) | fresh tokens only | cache reads + cache writes, **on top** |
| Codex rollouts (`CodexRolloutSync`, new) | `codex-cli` (recorded) | fresh tokens only | cached input, **on top** |
| Antigravity conversations (`AntigravityUsageSync`, new) | `antigravity-cli` (recorded) | input as agy reports it | — (agy does not expose it) |

- USD stays available internally (`eventCostUsd`, `getSessionUsageSince(...).cost`, the work item
  `cost` field) for code that needs it. Nothing owner-facing shows dollars.
- Owner text formats tokens as `12.4M tokens` (`services/usage/token-format.ts`), and accepts
  `20M`, `500k`, `1.5B`, `2000万`, `1亿` or a plain number.

Measured on the owner's Mac, 7 days to 2026-10-01: 7.0B tokens, of which 99.5% cached input (Claude
cache reads). Caps therefore have to be set with cache reads in mind: a long-lived Claude agent
re-reads its whole context every turn.

## 2. Sources

Every source writes `{ timestamp, session, runtime, model, input, cachedInput, output }` to the
shared ledger (`~/.crewly/token-usage.json`, `TokenUsageService`). Each new source is incremental
and idempotent, with a cursor file under CREWLY_HOME like the Claude transcript cursors.

### Codex (`services/monitoring/codex-rollout-sync.service.ts`)

- Codex writes `~/.codex/sessions/YYYY/MM/DD/rollout-<time>-<conversation id>.jsonl`. After each
  model call it appends `event_msg` / `token_count`; `info.total_token_usage` is the conversation's
  running total (OpenAI convention: `input_tokens` includes `cached_input_tokens`, `output_tokens`
  includes reasoning) and `info.last_token_usage` is that call. The model comes from the preceding
  `turn_context`.
- Each 60 s pass reads only the bytes appended since the last pass (byte cursor per file, whole
  lines only) and records the **delta of the running total**, so the `token_count` lines Codex
  repeats are counted once. The first total of a file, or a total that went down, records only
  `last_token_usage`.
- Attribution: Crewly persists each Codex agent's conversation id right after launch (the same id
  `codex resume` uses), so `…-<id>.jsonl` belongs to that session. A cursor keeps its session after
  the agent moves to a fresh conversation, so the old file's last turns still count. Rollouts no
  Crewly agent owns (the owner's own Codex use) are never read.
- Cursor file: `codex-rollout-cursors.json`.
- The activity monitor's PTY token parsing now skips Codex, so Codex is never counted twice.

### Antigravity (`services/monitoring/antigravity-usage-sync.service.ts`) — best effort

- agy keeps one SQLite database per conversation, `~/.gemini/antigravity-cli/conversations/<id>.db`.
  In its `steps` table, a model step's `metadata` blob is a protobuf whose field 9 is a usage
  message: input tokens in field 2, output in field 3. Field 1 is the step time.
- **The schema is not published.** It was read from agy 1.x databases on the owner's Mac (30 steps
  across 3 conversations decode to plausible counts, e.g. a one-word prompt = 12,719 in / 169 out).
  A blob without exactly that shape is skipped, never guessed. agy exposes no cached-input figure,
  and stores its model as an enum, so events use `antigravity-cli-default`.
- `agy --output-format stream-json` is print mode only. Crewly runs agy as an interactive PTY, so
  the database is the only source.
- Attribution: the conversation id Crewly records after launch. A per-conversation set of counted
  step indexes makes passes and restarts idempotent. A step whose usage is written later is picked
  up on a later pass. Cursor file: `antigravity-usage-cursors.json`.
- If agy changes the format, Antigravity usage silently stops being recorded (the rest is
  unaffected). That is the known gap.

## 3. Stats — `GET /api/system/usage`

`GET /api/system/usage?days=N&groupBy=agent|team|project|workItem|runtime|day`

- `days`: 1–31 local days, today included (1 = today; default 7). `groupBy` may be a comma list.
- Returns `{ days, since, today, totals, todayTotals, groupBy, rows, groups }`. `totals` and every
  row carry `{ input, cachedInput, output, total, events }` and rows add `{ key, label, share }`.
- Every event lands in exactly one row of a grouping, so each grouping sums to the total. Usage
  that cannot be attributed gets an `(unattributed)` row (the orc has no team: `Orc (no team)`).
- Attribution:
  - **team:** the session's team membership;
  - **work item:** each event goes to the work item that was active for its agent at the event's
    time (#953) — bounds as in `computeWorkItemUsage` (#812): `startedAt` (else `createdAt`) to
    `completedAt` (else now); an item that never started or completed has no span. When several
    of the agent's items span the event, the most recently started wins (ties: lowest id). Each
    item is listed once; usage outside any item goes to a `(no work item)` row. Top 50 items by
    tokens (plus that row), with title, agent, team, status and a `/workitems/<id>` link;
  - **project:** the work item running when the event happened, if it names a project
    (`metadata.projectId`) or its agent's team works on exactly one project; else the session's team
    when it works on exactly one project; else `(unattributed)`;
  - **runtime:** the runtime the source recorded, else inferred from the model id.
- Readable by agents (read-only).

### UI — Settings → System → Usage (`UsagePanel`, replaces `SpendPanel`)

Phone-first (stacked cards, no tables):

- period pills: **Today / 7 days / 30 days**;
- totals: tokens for the period and for today, cached input and output shown separately;
- **By team**: one card per team with usage, a cap or a boost: tokens for the period and today,
  its cap (`50M cap (+20M today)` / `Unlimited today` / `No cap`), **+X today** and
  **Unlimited today** (one tap), **End boost**, and the team-cap field; plus
  **Unlimited today for everyone** / **End everyone boost**;
- **By agent** (top 10, with team and runtimes), **By runtime** (with cached input), **Top work
  items** (top 10, linked);
- **Daily caps**: per agent (with the suggestion) and all agents together; **Save caps** also saves
  edited team caps.

## 4. Caps and boosts (`SpendCapService`)

### Store

`~/.crewly/usage-caps.json` (`FileSpendCapStore`, atomic writes):

```json
{
  "config": {
    "defaultAgentCapTokens": null,
    "totalCapTokens": null,
    "agentCapsTokens": { "crewly-orc": 5000000, "ella-…": null },
    "teamCapsTokens": { "5ad0642a-…": 50000000 }
  },
  "boosts": [
    { "id": "…", "target": "team:5ad0642a-…", "extraTokens": 20000000, "until": "2026-10-03T04:00:00.000Z", "createdAt": "…", "by": "orc-dm" }
  ],
  "day": { "date": "2026-10-02", "warned": [], "stopped": [], "cards": {} }
}
```

- Everything is **off by default**. `agentCapsTokens[session] = null` means no own cap for that
  agent even when a default is set.
- **Migration:** if `usage-caps.json` does not exist but the USD file `spend-caps.json` holds caps,
  they are converted once with `USAGE_CONSTANTS.TOKENS_PER_USD` (1,000,000 tokens per $1) and the
  conversion is logged (`Migrated daily spend caps from USD to tokens`). On the owner's Mac the USD
  caps were never set, so nothing is converted there.

### Caps

- **Agent:** its own cap (override › default). Counts that agent's tokens today.
- **Team:** `teamCapsTokens[teamId]`. Counts all its members' tokens today together. When reached,
  every member stops.
- **Total:** all agents together.
- An agent is stopped by the first cap it is over: own, then each of its teams, then the total.

### Boosts

- A boost covers an agent, a team (its members) or everyone (`*`).
- For every agent it covers, it adds `extraTokens` to **every** cap checked for that agent (own,
  team, total), or lifts them all (`unlimited`). Boosts add up.
- Notices and cards for a team cap count team and everyone boosts. Notices and cards for the total
  cap count everyone boosts only.
- It ends at `until`: by default the next **local midnight**. Expired boosts are dropped on read and
  logged. A stop that lifts (boost added, boost removed, midnight) releases queued messages.

Ways to set caps and boosts:

| Where | How |
|---|---|
| API (owner only) | `PUT /api/system/usage/caps` `{ defaultAgentCapTokens?, totalCapTokens?, agents?: { "<session>": n \| null \| "default" }, teams?: { "<teamId>": n \| null } }` |
| API (owner only) | `POST /api/system/usage/boost` `{ scope: "team" \| "agent" \| "all", id?, extraTokens? \| unlimited: true, until? }` (`id` = team id or name, agent session or name) |
| API (owner only) | `DELETE /api/system/usage/boost/:id` (end early) |
| API (read) | `GET /api/system/usage/caps?days=7`: caps, boosts, per-team and per-agent usage today, effective caps, stops |
| Settings → System → Usage | the panel above |
| Owner's DM with the orc | see below |

Kept for older clients: `GET /api/system/spend` (= `usage/caps`), `GET|PUT /api/system/spend/caps`.
`POST /api/system/spend/raise` answers **410** ("raises are boosts now").

Owner-only calls refuse any request carrying an agent session header (`ensureOwnerCaller`, 403):
an agent never raises its own budget.

### Orc-DM commands (`spend-cap-command.ts`)

Handled by the backend through a Slack bridge interceptor, so they work while the orc is stopped.
Replies are English; input may be English or Chinese. A target is `everyone` / `all` / `所有人` /
`全部` / `大家`, a team name (or id), or an agent name / session / `orc`. A name that is both a team
and an agent means the team. Free-text targets must look like a name (short ASCII) so an ordinary
sentence such as `放开那个文件的权限…` still goes to the orc.

| Command | Effect |
|---|---|
| `set daily cap for Ella to 5M` · `set daily cap to 5M` · `set daily total cap to 200M` | agent / default / total cap |
| `set team cap for CE to 50M` · `set daily cap for team CE to 50M` | team cap |
| `remove daily cap for Ella` · `remove team cap for CE` · `remove daily cap` · `remove daily total cap` | remove |
| `boost CE by 20M today` · `boost Ella +5M` · `give CE 20M more today` · `boost everyone by 10M` | +X until midnight |
| `unlimited today for everyone` · `unlimited today for CE` · `CE unlimited today` · `no cap for CE today` · `lift the cap for Ella today` | unlimited until midnight |
| `放开 CE 今天` · `今天放开 CE` · `今天全部放开` · `放开所有人` · `CE 今天不限` | unlimited until midnight |
| `给 CE 加 20M` · `今天给 Ella 加 2000万` · `CE 今天加 1亿` | +X until midnight |
| `set daily cap for orc to $5` (old dollar form) | one-line hint: caps are tokens now |

## 5. Enforcement

A tick runs every 60 s, and at once after any cap change, boost, or newly detected stop.

- **80%:** one heads-up per `target@cap` (agent, `team:<id>`, or `*`). A boosted cap gets its own.
  `Heads-up: Team CE has used 41M tokens of the 50M tokens daily token cap today (82%). At 50M its members stop taking new turns until midnight.`
- **100%: hard stop after the current turn.** `stopOf(session)` is live. It is the process-wide
  gate (`spend-cap.gate.ts`). **A capped agent takes no new turn from any delivery path.** Gates:

  | # | Where | What a capped agent gets |
  |---|---|---|
  | 1 | `sendMessageToAgent` (`/terminal/:s/deliver`, orc chat, queue flushes, …) | message queued on `SubAgentMessageQueue`, result `queued: true`, `[SPEND_CAP] …` |
  | 2 | `createAgentSession` | wake refused, `SPEND_CAP_REACHED` |
  | 3 | orc queue processor | held, re-checked every `QUEUE_RECHECK_MS` |
  | 4 | owner-message watchdog | a note instead of a nudge: `… hit its daily token cap (50M tokens for team CE) … boost it (reply \`boost CE by 10M today\` or \`unlimited today for CE\`)` |
  | 5 | `POST /terminal/:s/write` with `mode: "message"`, and any `/write` to an in-process runtime (#937) | queued as in 1 |
  | 6 | `POST /terminal/:s/deliver` with `force: true` (#937) | queued as in 1 |
  | 7 | `POST /sessions/:name/write` with `mode: "message"` (#937) | queued as in 1 |

  Gates 5–7 share `queueIfSpendCapped` (`services/messaging/spend-capped-delivery.ts`): the
  message goes on the same persistent `SubAgentMessageQueue` as gate 1, so the release below
  delivers it. They answer **202** `{ success: true, queued: true, spendCapped: true, message:
  "[SPEND_CAP] <reason>; message queued" }`. `/deliver` now answers the same 202 shape (with
  `verified: false`) whenever `sendMessageToAgent` queued the message, instead of
  `verified: true`. The agent `send-message` skill turns a queued answer into
  `delivered: false` with a "do not resend" note.

  **Not gated, by decision:** raw keystroke writes — `/terminal/:s/write` without
  `mode: "message"`, `/terminal/:s/key`, `/terminal/:s/input`, `/sessions/:name/write` without
  `mode: "message"`, and the UI terminal socket. They carry the control keys (Enter, Ctrl-C,
  Escape, a shell command) the owner and the services need to manage a stopped session; every
  message sender uses `mode: "message"` or `/deliver`.

  Known ungated paths (orchestrator notices typed with `TmuxService.sendMessage`, which is not a
  delivery path through the gate): team deletion and project team (un)assignment notices to the
  orc (`team.controller`, `project.controller`) and "run now" of a scheduled message
  (`scheduled-messages.controller`).
- **One decision card per stop** (kind `spend_cap`, `sensitive: 'spend'`, default = keep stopped,
  deadline = next local midnight):
  - question: `Team CE hit its daily token cap (50M tokens); its members are stopped until midnight. Boost it for today?`
  - options: **Boost +X tokens today** (X = the cap, rounded up to a whole million) ·
    **Unlimited today** · **Keep stopped**;
  - either boost option adds a boost on that target (`by: 'card'`) and answers in the card thread.
  - **withdrawn when the stop lifts without it** (#939): after each pass, a target in
    `day.cards` that is no longer over its cap (cap removed, raised above today's usage, total cap
    off, or a boost from the DM / API) has its card cancelled through `DecisionService.cancelWhere`
    with the note `no longer needed: …`, its entry dropped and its `day.stopped` keys cleared (a
    later stop posts a new card). An answered card is not open, so `cancelWhere` leaves it alone.
    A failed cancel logs a warning and is retried next pass; queued messages are released first.
    A new card for the same target (a changed cap that still stops it) withdraws the older one.
- **Capped orc:** every owner DM gets one harness line (`… To lift it for today, reply \`boost orc by 5M today\` or \`unlimited today for orc\` …`). The message itself stays queued.
- **Midnight:** the day's notices and cards reset, and default boosts expire. Caps stay.

## 6. Ticket autopilot budget in tokens

- `Project.ticketAutopilot.dailyBudgetTokens` replaces `dailyBudgetUsd`. The default is
  `TICKET_AUTOPILOT_CONSTANTS.DEFAULT_DAILY_BUDGET_TOKENS` = 20M, which equals the old $20 default
  at the migration rate.
- **Migration:** at boot, `TicketAutopilotService.migrateUsdBudgets()` converts every stored
  `dailyBudgetUsd` with `TOKENS_PER_USD`, saves the project and logs each conversion
  (`Ticket autopilot budget converted from USD to tokens`). Until then `resolveTicketAutopilotSettings`
  reads a stored USD value at the same rate. On the owner's Mac, CE's `$800` becomes `800M`.
- The API and the `project-tickets` skill take `dailyBudgetTokens` (`--daily-budget 20M`).
  `dailyBudgetUsd` input is refused with a hint.
- **Boosts:** today's budget = `dailyBudgetTokens` + the boosts on the project's teams (team and
  everyone boosts, each counted once), or unlimited. This is the same boost the caps use, so
  `boost CE by 20M today` also lets CE's autopilot triage again today.
- Status: `{ usedTodayTokens, budgetTodayTokens (null = unlimited), boostTokens, pausedForToday }`.
