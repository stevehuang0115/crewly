# Per-agent daily spend cap with a hard stop

Status: implemented (OSS `feat/spend-cap`, issue #853)
Date: 2026-10-02

## Why

In the last week the orchestrator (in-process Crewly Agent on DeepSeek) used up the owner's whole
DeepSeek balance. Status reports woke it 110–185 times a day, at about 70k input tokens per run.
The wake storm itself was fixed in 1.20.183 (#920). Nothing stopped an agent once it started
spending, though. Until now:

- `TeamBudgetGateService` is team-level only and refuses new work at claim time; it does not stop
  an agent that is already running;
- `BudgetService` (`services/autonomous/budget.service.ts`) is dead code (nothing records into it);
- the ticket autopilot has a per-project daily budget, but it only pauses its own triage wakes;
- the runtime fallback (1.20.177/178) reacts to a **provider's** usage limit or billing error by
  switching runtimes.

A spend cap is different from all of these: it is **the owner's own limit**, per agent, per local day,
and it stops the agent.

## 1. Spend first (`SpendLedger`)

`services/spend/spend-ledger.service.ts` gives per-agent, per-runtime and per-local-day cost in USD,
read from the shared token ledger (`~/.crewly/token-usage.json`, kept in memory by
`TokenUsageService`). Both sources of agent usage write to that ledger:

| Source | Event shape | Pricing |
|---|---|---|
| In-process Crewly Agent runs (DeepSeek, …), `model = provider/model` | `cachedInput` is the cache-hit **part of** `input` | `TOKEN_COSTS` (cache-aware DeepSeek rates) |
| Claude Code turns (`ClaudeTranscriptSync`) | `input` is fresh tokens only; `cachedInput` = cache reads + `cacheWrite`, **on top of** `input` | `model-pricing` (opus / sonnet / haiku / fable tiers, cache read and write rates) |
| Codex / Gemini PTY parsing (activity monitor) | input / output only | `TOKEN_COSTS` |

**One cost computation.** `eventCostUsd(event)` in `token-usage.service.ts` prices one event from
either shape. `getSessionUsageSince` now uses it, so the ticket autopilot's daily budget, the team
budget gate and the spend cap all read the same number. Before this change `getSessionUsageSince`
priced Claude events with the legacy table. That table drops every cached token and has no
`claude-opus-5-5` entry, so it fell back to sonnet rates. A long-lived Claude agent was
under-counted roughly 50–100×. The Usage dashboard was already cache-aware for Claude, through the
transcript sync's session cost override. Now the budgets match it.

> Note: Claude Code under a subscription is not billed at these rates. Its figure is the
> API-equivalent cost, labelled as such in the UI.

The runtime of an event is inferred from its model id (`provider/model` → `crewly-agent`,
`claude-*`/`opus`/`sonnet`/`haiku`/`fable` → `claude-code`, `gpt`/`codex` → `codex-cli`,
`gemini` → `gemini-cli`, `<runtime>-default` → that runtime).

### API

`GET /api/system/spend?days=7` (1–31, default 7) returns:

- `days[]`: `{ date, totalUsd, byAgent, byRuntime }`, oldest first, ending today (local);
- `agents[]`: `{ session, name, runtimes, todayUsd, windowUsd, daily[], capUsd, capSource, stopped, stopReason? }`;
- `byRuntime`, `totalUsd`, `todayUsd`;
- `p90AgentDayUsd` and `suggestedAgentCapUsd`: the 90th percentile of per-agent daily spend over
  agent-days with any spend, rounded up to whole dollars;
- `caps`, `raisedToday`, `totalCapTodayUsd`, `totalStopped`.

The GET routes are readable by agents. Changes are owner-only (see §2).

### UI

Settings → System → **Spend** (`SpendPanel`), phone-first (single column, wraps at 320px):

- Today and last-7-days totals, each split by runtime;
- one card per agent (with spend, a cap or a stop) showing today, 7 days, its cap and where the cap
  comes from, its stop reason, a cap override field and **Raise to $Y today** when stopped;
- default per-agent cap (with **Use suggested $N**), the optional total cap, and **Save caps**.

## 2. Caps

`~/.crewly/spend-caps.json` (`FileSpendCapStore`, written atomically):

```json
{
  "config": {
    "defaultAgentCapUsd": null,
    "totalCapUsd": null,
    "agentCapsUsd": { "crewly-orc": 5, "ella-…": null }
  },
  "day": { "date": "2026-10-02", "raised": {}, "warned": [], "stopped": [], "cards": {} }
}
```

- Everything is **off by default** (`null`).
- `agentCapsUsd[session]`: a number is that agent's own cap; `null` means *no cap for this agent*,
  even when a default is set.
- Cap in force today = today's raise › own cap › default cap. The total cap applies to all agents
  together.

Ways to set them:

| Where | How |
|---|---|
| API (owner only) | `PUT /api/system/spend/caps` `{ defaultAgentCapUsd?, totalCapUsd?, agents?: { "<session>": number \| null \| "default" } }` |
| API (owner only) | `POST /api/system/spend/raise` `{ session: "<session>" \| "*", capUsd }`, for today only; must be above today's spend |
| Settings → System → Spend | the panel above |
| Owner's DM with the orc | `set daily cap for crewly-orc to $5` · `set daily cap to $5` (default) · `set daily total cap to $20` · `remove daily cap for Ella` · `remove daily cap` · `remove daily total cap` · `raise cap for orc to $10 today` · `raise total cap to $40 today` |

The DM commands are handled by the backend through a Slack bridge interceptor (as with
skip-all-cards), not by the orc, so they still work while the orc is stopped. Agents are named by
member name, session name, or `orc` / `orchestrator`. Owner-only API calls refuse any request that
carries an agent session header (`ensureOwnerCaller`, 403): an agent never raises its own budget.

## 3. Enforcement (`SpendCapService`)

A tick runs every 60 s, plus at once after any cap change, raise, or newly detected stop.

- **80%:** one heads-up to the owner (Slack DM from this machine's orc bot), once per
  `target@cap`. A raised cap therefore gets its own heads-up.
  `Heads-up: Orc has spent $4.10 of its $5.00 daily spend cap today (82%). At $5.00 it stops taking new turns until midnight.`
- **100%: hard stop.** `stopOf(session)` is **live**: it reads today's spend on every call and does
  not wait for the tick. It is installed as the process-wide gate (`spend-cap.gate.ts`) and checked
  in four places:
  1. `AgentRegistrationService.sendMessageToAgent`: the message goes to the persistent
     `SubAgentMessageQueue` (`[SPEND_CAP] … message queued`) and no turn starts. A turn already
     running is never interrupted; it finishes, then the session idles.
  2. `AgentRegistrationService.createAgentSession`: waking a capped agent is refused with the
     reason (`errorCode: SPEND_CAP_REACHED`). The orchestrator's session may still start, because an
     idle session costs nothing; gates 1 and 3 hold its turns.
  3. `QueueProcessorService.processNext`: the orchestrator's message queue is held (rechecked every
     60 s). Messages stay queued in order.
  4. The owner-message watchdog: at T1 it does not nudge a capped agent. It posts one note:
     `⏳ Still waiting on Ella — Ella hit its daily spend cap ($5.00). Your message is kept and delivered when the cap resets at midnight or you raise it (reply \`raise cap for Ella to $<amount> today\`).`
- **One decision card** per stop (`DecisionService.askSystem`, kind `spend_cap`, owner's DM with the
  orc bot, `sensitive: 'spend'`, `defaultIsDecline: true`, deadline = next local midnight):
  - question: `Ella hit its daily spend cap ($5.00) and is stopped until midnight. Raise it for today?`
  - options: **Raise to $Y today** (Y = cap × 2, rounded up to whole dollars, always above today's
    spend) · **Keep stopped** (the default)
  - Raise → `raiseToday`; the card thread gets `Raised Ella's cap to $10.00 for today. Queued messages are being delivered.`
  - A card from an earlier day is ignored, with a note in its thread.
  - If decision cards are not wired, a plain notice with the DM command is sent instead.
- **Owner DMs to a capped orc:** every one gets a one-line harness reply. The message is not
  consumed: it goes on to the orc's queue and waits there.
  `Orc hit its daily spend cap ($5.00). No new turns start until midnight; your message is queued. To raise it for today, reply \`raise cap for orc to $10 today\` (or Settings → System → Spend).`
- **Total cap:** when all agents together reach it, every agent is stopped (scope `total`), with
  one card for the total.
- **Reset at local midnight:** `day` is cleared (raises, notices, cards); the caps themselves stay.
- **Release:** when a stop lifts (midnight, raise, or cap change), each released agent's queued
  messages are flushed into its live session. A stopped team member is activated instead, and
  registration flushes its queue. The orc's held queue resumes on its next check.

### Not a runtime fallback

The runtime fallback moves an agent to another runtime when a provider says "out of usage". A spend
cap never switches runtimes. It stops the agent.

## 4. One budget path

- Cost: one function (`eventCostUsd`) behind `getSessionUsageSince`, used by the ticket autopilot,
  the team budget gate and the spend cap.
- Enforcement: the team gate refuses new work at claim time per team (monthly USD / daily tokens).
  The spend cap stops the agent itself per day. The two are complementary.
- `BudgetService` is still dead code. Removing it, and its fission-guard read, is left for a
  follow-up so this change stays clear of the concurrent dispatch work.
